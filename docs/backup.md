# Копия базы данных

Раз в неделю сайт сам делает копию всей базы и присылает её файлом владельцу в Telegram.
Копия нужна на случай, если с базой у поставщика что-то случится: по ней все данные
можно вернуть.

## Где лежат копии

В личном чате владельца с ботом сайта — там же, куда приходят заявки. Каждый понедельник
ночью приходит файл с названием вида `iistroyka24-2026-11-16-0340-1of1.bkp` и подписью:

```
Копия базы «ИИСтройка24» от 16.11.2026 03:40 МСК
Таблиц: 41, строк: 12 345, размер: 1,2 МБ
Проверка восстановления пройдена ✅
```

- Файлы из чата удалять не нужно: чем их больше, тем дальше назад можно вернуться.
- Если копия большая, она приходит несколькими файлами: «Часть 1 из 3», «Часть 2 из 3»…
  У частей одной копии одинаковые дата и время в названии. Для восстановления нужны все.
- GitHub запускает задание с опозданием, иногда на несколько часов, — это нормально.
- Если вместо файла пришло «Копия базы … не создана» или в понедельник не пришло ничего —
  сообщите разработчику сайта. Сайт при этом работает как обычно.

«Проверка восстановления пройдена» значит: сразу после создания сайт сам расшифровал
копию, распаковал её и сверил число строк в каждой таблице с базой.

## Ключ

Файл зашифрован. Ключ — значение переменной `CRON_SECRET` (оно записано в настройках
Vercel и в секретах GitHub).

**Запишите это значение в надёжное место** — в менеджер паролей или на бумагу в сейф.
Без него копию не открыть никому, и нам тоже.

Если `CRON_SECRET` когда-нибудь поменяется, новые копии будут шифроваться новым значением,
а старые по-прежнему открываются только старым. Поэтому старое значение не выбрасывайте:
запишите рядом с ним дату, до которой оно действовало.

## Как проверить копию

Нужен компьютер с этим репозиторием (`pnpm install`). Скачайте файл из чата и выполните:

```
CRON_SECRET='значение ключа' pnpm --filter @specai/database restore-backup /путь/к/файлу.bkp
```

Если частей несколько, перечислите через пробел все. Команда ничего не меняет и ни к какой
базе не подключается: она расшифровывает копию и печатает, сколько строк в каждой таблице.

## Как восстановить базу

Копия записывается только в **пустую** базу. Если в базе есть хоть одна строка, команда
откажется и ничего не изменит — так нельзя случайно затереть рабочие данные.

1. Создайте новую пустую базу PostgreSQL (у того же или у другого поставщика) и возьмите
   её адрес — строку вида `postgresql://…`. Нужен прямой адрес, без «pooler» в имени.
2. Создайте в ней пустые таблицы:

   ```
   cd packages/database
   DATABASE_URL='адрес новой базы' DIRECT_URL='адрес новой базы' npx prisma db push --skip-generate
   ```

3. Запишите копию:

   ```
   CRON_SECRET='значение ключа' RESTORE_DATABASE_URL='адрес новой базы' \
     pnpm --filter @specai/database restore-backup /путь/к/файлу.bkp --write
   ```

   В конце команда печатает число строк по таблицам уже в новой базе. Если что-то пойдёт
   не так, она скажет, что именно, а база останется пустой — можно исправить и повторить.

4. Укажите адрес новой базы в настройках Vercel (`DATABASE_URL` и `DIRECT_URL`; если заданы
   `NEON_DATABASE_URL` и `NEON_DATABASE_URL_UNPOOLED` — их тоже, они главнее) и сделайте
   Redeploy. После него откройте `https://иистройка24.рф/api/categories` — должен быть ответ 200.

Всё, что появилось на сайте после даты копии, в неё не входит.

## Что говорят сообщения команды

| Сообщение                            | Что делать                                                         |
| ------------------------------------ | ------------------------------------------------------------------ |
| «Ключ не подходит…»                  | Указано не то значение `CRON_SECRET`, что действовало в день копии |
| «Файл копии повреждён…»              | Скачайте файл из чата заново                                       |
| «Не хватает частей копии: 2 из 3»    | Скачайте и укажите все части                                       |
| «В базе уже есть данные…»            | Создайте новую пустую базу                                         |
| «Таблицы базы не совпадают с копией» | Повторите шаг 2 для новой базы                                     |

## Как это устроено (для разработчиков)

- Расписание: `.github/workflows/backup.yml` раз в неделю вызывает `GET /api/cron/backup`
  с `CRON_SECRET`. Через GitHub сама копия не проходит: задание ничего не сохраняет и
  печатает только числа.
- Маршрут `apps/web/src/app/api/cron/backup/route.ts`: только на продакшене, одна копия в
  сутки (`lib/cronOnce.ts`), в ответе и журнале — только числа.
- Чтение базы, формат файла, шифрование и проверка — `packages/database/src/backup/`;
  восстановление — `packages/database/scripts/restore-backup.ts`.
- Таблицы берутся из самой базы, поэтому новая модель попадает в копию без правок кода.
- Копия делается за одно выполнение функции (60 секунд). Когда база вырастет так, что
  перестанет укладываться, владельцу придёт «Копия базы … не создана» — тогда копию надо
  переносить на другой способ запуска.
